Especificación: Skill traza-requisitos-modelo

§1 Resumen

Construir una skill que construye la matriz de trazabilidad bidireccional del proyecto: cada restricción/regla del análisis de dominio (agricultural-analysis.md) — entrada multimodal, reglas plaga-cultivo-clima-región, tolerancia al error, nivel de confianza, validación humana — conectada con la capability de clean-architecture.md, la entidad/atributo del modelo (data-model-mvp.md) y el patrón de diseño de possible-design-patterns.md que la soporta; y a la inversa, cada elemento del modelo/capability con el requisito que lo origina. Es la respuesta automática a "¿nuestro diseño cubre lo que dijimos que íbamos a cubrir, y cada cosa del diseño responde a un requisito?".

§2 Objetivos

  • O1. Existe skills/traza-requisitos-modelo/SKILL.md con frontmatter name: traza-requisitos-modelo y description en una sola línea, sin placeholders ni TODO.
  • O2. La skill lee las cuatro fuentes: requisitos (docs/01-architecture/agricultural-analysis.md), capabilities (docs/01-architecture/clean-architecture.md), modelo de datos (docs/02-data/data-model-mvp.md) y patrones (docs/02-data/possible-design-patterns.md).
  • O3. La granularidad es por regla/restricción: cada restricción concreta del doc de requisitos es una fila de la matriz; ninguna sección queda tratada "en bruto" como un solo requisito.
  • O4. La traza es bidireccional: cada requisito lleva estado cubierto / parcial / sin soporte con la evidencia (capability, entidad/atributo, patrón); cada capability y cada entidad principal lleva su requisito de origen; los huérfanos en ambas direcciones se reportan.
  • O5. Los patrones participan como evidencia de soporte: cada capability con un patrón candidato de possible-design-patterns.md; una capability sin patrón asignable se reporta como brecha de diseño, no se inventa.
  • O6. En read-only no modifica ningún archivo: git status queda limpio. En modo corrección solo edita los docs de modelo/capabilities con confirmación por fila; el doc de requisitos nunca se toca.
  • O7. Un requisito sin soporte se marca como brecha de alcance: se reporta y se pregunta, jamás se inventa un soporte plausible para tapar la brecha.
  • O8. Queda instalada en skills/traza-requisitos-modelo/ (repo), ~/.opencode/skills/ y ~/.agents/skills/, y empaquetada como traza-requisitos-modelo.skill (verificable con ls y unzip -l).

§3 Fuera de alcance

  • No se modifica el doc de requisitos: las restricciones del dominio son decisiones del dueño, no erratas corregibles por la skill.
  • No se crean capabilities ni entidades para cerrar brechas: la trazabilidad reporta; el diseño lo decide el dueño.
  • No se definen los patrones (eso vive en possible-design-patterns.md y clean-architecture.md); la skill solo los asigna como evidencia.
  • No se detecta drift entre modelo y SQL/diagrama (eso es valida-diccionario-datos y concuerda-docs-diagramas), ni coherencia de AGENTS.md contra el árbol (es audita-agents-md).

§4 Diseño

La skill ejecuta 5 pasos: inventariar y leer las cuatro fuentes, extraer los requisitos (por regla), extraer capabilities/entidades/atributos y patrones candidatos, construir la matriz bidireccional, y emitir el reporte; en modo corrección, editar los docs de modelo/capabilities con confirmación y re-auditar. Regla de contraste: el soporte se evidencia con nombres explícitos (capability, entidad, atributo, patrón); si no hay nombre, no hay soporte.

Reglas que debe codificar la skill:

  • Requisito por regla: se descompone cada sección del doc de requisitos en restricciones/reglas concretas (una entrada multimodal, una regla de plaga-cultivo-clima-región, la tolerancia al error, el nivel de confianza, la validación humana…). Cada regla se referencia a su línea/sección de origen.
  • Estado de soporte: cubierto si existe evidencia de capability + elemento de modelo + patrón; parcial si falta al menos un eslabón; sin soporte si no hay evidencia con nombre en ninguna capa.
  • Evidencia por nombre: el soporte se cita con el nombre real (p. ej. capability diagnoses, entidad Diagnóstico, patrón Facade/Use Case). Afirmaciones sin nombre no son evidencia.
  • Traza inversa: cada capability y cada entidad principal declara su requisito de origen; si el elemento proviene de una convención o de la arquitectura y no de un requisito de dominio, se marca "origen: convención/arquitectura" en vez de dejarlo huérfano sin explicación.
  • Patrón como apoyo: se asigna a cada capability el patrón candidato de possible-design-patterns.md que le corresponde; una capability sin patrón asignable es una brecha de diseño reportada.
  • Brecha de alcance: un requisito sin soporte se lista como brecha de alcance y se pregunta al dueño (¿se implementa en el MVP, se difiere, o era ruido?); nunca se inventa soporte para taparla.

§5 Casos borde

CasoComportamiento esperado
Requisito con soporte incompleto (falta una capa)Estado parcial; la fila indica qué eslabón falta (capability, entidad/atributo o patrón).
Requisito sin evidencia con nombre en ninguna capaEstado sin soporte; se lista como brecha de alcance y se pregunta si va al MVP, se difiere o es ruido.
Capability sin patrón asignable en el doc de patronesFila de brecha de diseño: no se inventa el patrón; se reporta para decidir en la doc de patrones.
Elemento del modelo que no proviene de un requisitoSe marca "origen: convención/arquitectura" cuando una convención lo justifica; si no, se reporta como huérfano.
Requisito ambiguo o no verificable en el modeloSe marca no evaluable y se pregunta al dueño si es requisito o ruido del documento.
Doc de requisitos ausente o vacíoSe aborta con aviso y se pregunta si debe crearse (crearlo queda fuera del alcance), en vez de inventar la matriz.
Doc de patrones ausenteLa evidencia de patrones se omite del soporte y se reporta la ausencia; las demás capas se trazan igual.
Corrección confirmada que rompe otra secciónEl re-audit lo detecta; los cambios se aplican por fila, no en bloque.
Matriz muy grandeResumen con conteos por estado (cubierto/parcial/sin soporte) al inicio; detalle completo después.

§7 Decisiones

Capas que conecta la traza Requisitos → capabilities → modelo de datos + patrones como evidencia Solo requisitos → modelo; sin patrones Saltar la capa de capabilities hace la traza ciega a la arquitectura; omitir los patrones deja el "cómo se implementa" sin verificar.
Granularidad del requisito Cada regla/restricción concreta es una fila trazable Tratar una sección completa como un requisito Una sección "en bloque" oculta qué restricción quedó sin soporte; por regla la brecha es localizable.
Dirección de la traza Bidireccional: requisito → soporte y elemento → origen Solo forward (requisito → soporte) Sin la traza inversa no se descubre "diseño sin motivo", que es donde se cuela el oro y el acceso no que ningún requisito pidió.
