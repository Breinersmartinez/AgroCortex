Especificación: Skill crear-especificacion

§1 Resumen

Construir una skill que convierte una petición suelta —tarea, feature, proyecto o encargo— en una especificación verificable: un único HTML autocontenido en español con siete secciones fijas y diagramas en SVG. La skill no hace el trabajo: especifica qué hay que construir, para quién y cómo se sabrá que quedó bien, cerrando las decisiones que el solicitante no haya tomado en silencio. Es reutilizable en cualquier proyecto y no depende de conocimiento específico del dominio donde se use.

§2 Objetivos

  • O1. Existe .opencode/skills/crear-especificacion/SKILL.md con frontmatter name: crear-especificacion y description en una sola línea, sin placeholders ni TODO.
  • O2. La skill recibe la petición tal como la dijo el usuario y ejecuta una entrevista de cierre mínima: objetivo real, quién recibe el resultado, contexto, restricciones, preocupaciones y lo ya intentado.
  • O3. Emite un único archivo HTML autocontenido en español con las siete secciones obligatorias en orden: §1 Resumen, §2 Objetivos (medibles), §3 Fuera de alcance (nunca vacía), §4 Diseño (con diagrama SVG obligatorio si el flujo supera los tres pasos), §5 Casos borde (caso + comportamiento esperado), §6 Criterios de aceptación (sí/no, ejecutables por un tercero), §7 Decisiones (elegido / descartado / porqué).
  • O4. Ninguna decisión se asume en silencio: lo que no se puede deducir del contexto se pregunta antes de entregar; cada decisión cerrada se registra en §7.
  • O5. Antes de entregar, la especificación se somete a las tres preguntas de validación (decisión sin argumentar, sección plana, implementable sin estar en la conversación); si alguna falla, se vuelve a la entrevista.
  • O6. La skill es genérica: no contiene nombres ni reglas específicas de ningún proyecto; el conocimiento de dominio entra solo vía el contexto de ejecución.
  • O7. Queda instalada en .opencode/skills/crear-especificacion/ (repo), ~/.opencode/skills/ y ~/.agents/skills/.

§3 Fuera de alcance

  • No implementa la solución: el entregable es la especificación, no código ni artefactos de aplicación.
  • No inventa decisiones: si el usuario no respondió algo que afecta el resultado, se pregunta o se declara la omisión; nunca se rellena con un valor plausible.
  • No produce entregables con dependencias externas: el HTML es autocontenido (sin cargas remotas, sin JavaScript requerido).
  • No define diagramas raster ni capturas: solo SVG embebido.

§4 Diseño

La skill ejecuta 5 pasos: recibir la petición tal cual, entrevista de cierre de decisiones, redacción con la plantilla de references/plantilla-especificacion.html, auto-auditoría con las tres preguntas, y entrega del HTML final. Si la auditoría revela una decisión nueva, se vuelve al usuario y se re-abre el ciclo.

Reglas que debe codificar la skill:

  • No se asumen decisiones: si una decisión no se puede deducir del contexto y no se ha preguntado, se pregunta; nunca se rellena con un valor plausible.
  • Siete secciones obligatorias: Resumen, Objetivos, Fuera de alcance, Diseño, Casos borde, Criterios de aceptación, Decisiones — en ese orden y todas presentes.
  • Criterios sí/no ejecutables: cada criterio de §6 se responde con sí o no con una comprobación que otra persona pueda ejecutar sin estar en la conversación.
  • Decisiones con porqué: cada fila de §7 documenta la duda, lo elegido, lo descartado y la razón, para que sirva dentro de seis meses.
  • Auto-auditoría previa a la entrega: ¿qué decisión estoy tomando sin argumentar?, ¿qué sección está plana?, ¿podría implementarlo alguien que no estuvo en la conversación?
