Especificación: Skill documenta-codigo

§1 Resumen

Construir una skill que detecta código backend Java sin documentación pública y propone Javadoc para las clases y métodos que las reglas del proyecto sí deben documentarse (dominio, puertos, casos de uso, adaptadores, controllers), read-only por defecto y aplicando con confirmación por archivo. Incluye reglas de qué no comentar: la documentación describe el contrato/capacidad, no la implementación. Por qué existe: docs/01-architecture/clean-architecture.md exige un dominio sin Spring ni JPA y javadoc coherente; nada de esto está estandarizado hoy.

§2 Objetivos

  • O1. Existe skills/documenta-codigo/SKILL.md con frontmatter name: documenta-codigo y description en una sola línea, sin placeholders ni TODO.
  • O2. Escanea backend/src/main/java (arquivos *.java) y clasifica elementos públicos: paquetes, clases y métodos públicos de puertos, casos de uso, adaptadores y controllers; detecta la ausencia de Javadoc.
  • O3. Propone por archivo un Javadoc de 1-3 líneas que describe el contrato o la capacidad en español (idioma del repo), con @param/@return cuando aportan información y no son tontos.
  • O4. Respeta la regla de "no comentar": no genera Javadoc para elementos privados ni getters/setters triviales, no documenta lógica obvia y no añade comentarios de línea repetitivos.
  • O5. Por defecto solo reporta (read-only); aplica los Javadoc solo con confirmación explícita por archivo y no toca nada más del archivo (sin refactor, sin embellecer).
  • O6. Instalada en skills/documenta-codigo/ (repo), ~/.opencode/skills/ y ~/.agents/skills/, empaquetada como documenta-codigo.skill (verificable con unzip -l).

§3 Fuera de alcance

  • No refactoriza código ni cambia su estructura; si el archivo necesita refactor, se dice pero no se hace.
  • No toca frontend TypeScript: esta skill es de backend Java; el frontend se documentaría con otra skill.
  • No comenta lógica obvia, getters/setters triviales ni implementaciones legibles por sí mismas.
  • No genera documentación de API HTTP (eso es responsabilidad de springdoc/Swagger, ya presente en el pom).
  • No corrige estilo de código, nombres ni imports (eso sería otra herramienta).

§4 Diseño

La skill ejecuta 5 pasos: escanear el árbol backend/src/main/java, clasificar los elementos públicos, redactar las propuestas de Javadoc, aplicar con confirmación (solo en el modo autorizado) y volver a escanear para verificar. Todos los Javadoc describen el contrato, no la implementación.

Reglas que debe codificar la skill:

  • Qué se documenta (públicos): clases e interfaces de dominio (entidades, value objects, enums de negocio), puertos (interfaces de aplicación y de adaptadores), casos de uso, adaptadores y controllers (API fina). También paquetes con package-info.java si existe el convenio en el repo.
  • Qué NO se documenta: getters/setters triviales, elementos privados/protegidos, overrides que ya heredan contrato (salvo que aporten algo nuevo), e implementaciones que se explican solas (regla "no comentar lo obvio").
  • Contrato, no implementación: el Javadoc dice qué hace/tiene la pieza y qué garantiza, no cómo lo hace; en adaptadores se menciona el "hacia qué sistema" (p. ej. base de datos, modelo LLM).
  • Estilo: 1-3 líneas en español, minúscula inicial, sin saludo, con @param/@return solo cuando aportan (no se documenta @param nombre el nombre). Sin duplicar lo que ya dice el tipo.
  • Modo por defecto = reporte read-only: lista por archivo los elementos sin documentar y la propuesta; aplicar requiere confirmación por archivo.
  • No refactor: la edición solo inserta los bloques Javadoc; no reformatea ni reordena nada del archivo.

§5 Casos borde

CasoComportamiento esperado
Archivo sin elementos públicosSe reporta como exento sin proponer nada.
Clase ya totalmente documentadaNo se toca; se lista como "ya documentada".
Método override con contrato heredadoNo se genera Javadoc nuevo salvo que el override aporte comportamiento distinto.
Javadoc parcial de un método (falta @param informativo)Se propone solo completar la parte faltante.
Comentarios de línea existentes contradictorios con el contratoSe reporta la contradicción sin duplicar el comentario y sin borrar lo existente.
El archivo está en un paquete de red de solo dominioSe documenta solo lo que la regla pide (el dominio no se acopla a nada; los Javadoc no mencionan Spring/JPA).

§7 Decisiones

Duda que aparecióSe eligióSe descartóPor qué
Estructura de entregables Skills separadas: formatea-commits y documenta-codigo Una skill con dos modos Cada skill un propósito: la de commits no se acopla a la semántica de Javadoc y viceversa.
Alcance del código a documentar Solo backend Java (dominio, puertos, UC, adaptadores, controllers) Backend + frontend TS El backend es el que tiene entidades/puertos próximos y la deuda de javadoc; el frontend aún no tiene servicios ni rutas (scaffold).
Comportamiento Propone por archivo y aplica con confirmación (read-only por defecto) Solo reporte; aplicar directo sin confirmar Consistente con la familia de auditoría: la propuesta se ve, el quitar el "no tocar" lo decide el usuario por archivo.
Qué se comenta Contrato/capacidad, no implementación Javadoc exhaustivo de todo La doc que explica el "qué" sobrevive al refactor; la que explica el "cómo" se pudre y duplica el código.
Idioma y estilo Español, 1-3 líneas, @param/@return solo si aportan Inglés; doc extensa; parámetros documentados de forma genérica El repo está en español; un Javadoc breve y sin ruido se mantiene al día y se aprueba en review.
