Especificación: Skill formatea-commits

§1 Resumen

Construir una skill que sugiere y valida mensajes de commit del monorepo AgroCortex siguiendo docs/06-contribution/git-commit-prefixes.md (Conventional Commits: tipo(ámbito): descripción). Analiza el diff y genera el mensaje con tipo y ámbito correctos, y comprueba mensajes ya escritos contra el formato. La skill nunca ejecuta git commit: entrega el mensaje listo. La prueba de que hace falta: la convención existe en el doc pero nada la aplica ni la comprueba.

§2 Objetivos

  • O1. Existe skills/formatea-commits/SKILL.md con frontmatter name: formatea-commits y description en una sola línea, sin placeholders ni TODO.
  • O2. La fuente única del formato es docs/06-contribution/git-commit-prefixes.md: la skill la lee y si el doc cambia, la skill obedece el cambio (no tiene el formato copiado como dogma).
  • O3. Modo generar: lee git diff --staged (y trabaja con el working tree si no hay staged) e infiere tipo + ámbito por componente y contenido; entrega un mensaje tipo(ámbito): verbo imperativo en minúsculas en español, breve (≤50 caracteres el título).
  • O4. Modo validar: comprueba un mensaje dado contra el formato y reporta cada violación (tipo desconocido, falta de colon+espacio, mayúscula inicial, no-imperativo, título muy largo) con el mensaje corregido propuesto.
  • O5. La skill jamás ejecuta git commit, amend ni push: entrega el mensaje y le deja el commit al usuario.
  • O6. Instalada en skills/formatea-commits/ (repo), ~/.opencode/skills/ y ~/.agents/skills/, empaquetada como formatea-commits.skill (verificable con unzip -l).

§3 Fuera de alcance

  • No ejecuta git commit nunca, ni siquiera con confirmación.
  • No reescribe commits existentes (sin amend, sin rebase, sin force push).
  • No gestiona Git: no hace push, merge ni resuelve conflictos.
  • No documenta código (eso es documenta-codigo).
  • No decide el tipo cuando el cambio es genuinamente ambiguo: elige el más probable y lo marca para que el usuario lo revise.

§4 Diseño

La skill ejecuta 5 pasos: leer la convención, capturar el intento de cambio, inferir tipo y ámbito, generar (o validar) el mensaje y presentarlo listo para copiar. Los modos generar y validar comparten la taxonomía del doc de convención.

Reglas que debe codificar la skill:

  • Taxonomía: los tipos salen del doc (feat, fix, docs, style, refactor, perf, test, chore, build, ci); un tipo no listado se reporta en validación.
  • Inferencia de tipo: predominancia por paths y contenido: .github/workflows → ci; deps (pom.xml, package.json) → build o chore según dependencia vs tooling; solo docs → docs; pruebas → test; sql/migraciones → chore o feat según contenido; java/ts de negocio → feat/fix según el diff.
  • Ámbito: si el cambio toca un módulo dominante (auth, farmers/sembradios, crops, consultations, diagnoses, docs, ci, backend, frontend…), va el ámbito; si toca transversal, sin ámbito o con el componente mayoritário y la marca "revise".
  • Descripción: imperativo en español, minúsculas (salvo nombres propios), título ≤50 caracteres; se puede ofrecer un cuerpo corto tras una línea en blanco cuando el diff lo pida.
  • Validación: regex ^(feat|fix|docs|style|refactor|perf|test|chore|build|ci)(\([a-z0-9-]+\))?: .+ contra el título; cada violación se reporta con el ejemplo corregido.

§5 Casos borde

CasoComportamiento esperado
Nada staged y working tree limpioAvisa que no hay cambios que formatear y termina.
Cambios en varios módulos a la vezElige el tipo/ámbito del módulo mayoritário, lista los demás en el cuerpo y marca "revise" si el reparto es dudoso.
Tipo ambiguo (deps + tooling)Propone el más probable (build vs chore) con justificación de una línea y lo marca para revisar.
Mensaje a validar en mayúscula o no-imperativoReporta la violación concreta y entrega el mensaje corregido manteniendo el contenido.
Título >50 caracteres al validarReporta longitud y propone una versión más corta.
Commit tipo mergeAvisa que los commits de merge no llevan tipo Conventional Commits y no los formatea.
Diff que solo toca docsÁmbito docs y tipo docs, salvo que el cambio de doc afecte otra categoría reportada.
Descripción con nombre propio (p. ej. "Sembradio")Se respeta la mayúscula del nombre propio dentro de la minúscula general.

§7 Decisiones

Duda que aparecióSe eligióSe descartóPor qué
Estructura de entregables Skills separadas: formatea-commits y documenta-codigo Una skill con dos modos Un propósito, una skill: la validación e instalación independiente evitan que un cambio de convención de commits arrastre reglas de documentación de código.
Comportamiento de commits Sugerir + validar mensajes Solo lint; solo generar Para la convención ya documentada, tanto generar como comprobar cuestan lo mismo y cubren el ciclo: escribir bien y verificar lo escrito.
¿La skill commitea? Nunca ejecuta git commit Auto-commit con confirmación El commit es una decisión del autor sobre su historial; la skill entrega el mensaje y respeta la barrera de `main` protegida.
Fuente del formato El doc git-commit-prefixes.md es la fuente única Formato endurecido en la skill Si el doc de convención cambia, la skill lo obedece sin reescribir la skill; el doc manda, la skill traduce.
Idioma de la descripción Español, imperativo, minúsculas Inglés; singular sustantivos El repo y su documentación están en español; el imperativo es el que pide el formato Conventional Commits.
