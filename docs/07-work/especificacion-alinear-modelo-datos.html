Especificación: Alinear el modelo de datos RBAC

§1 Resumen

Alinear las migraciones RBAC (V1/V2) con las convenciones del modelo de datos: renombrar las columnas de auditoría al español (creado_en/actualizado_en), renombrar los permisos FIELDS_* a SEMBRADIOS_* y completar los permisos faltantes (EVIDENCE_UPDATE, DIAGNOSES_DELETE, RECOMMENDATIONS_DELETE) con su asignación a roles. Todo se resuelve con una migración nueva, aditiva e idempotente, sin tocar V1/V2 ni romper el historial de Flyway. Hoy las tablas app_* nacen en inglés y con un catálogo incompleto, contradiciendo la fuente única docs/02-data/data-model-mvp.md; quien toque el código mañana paga esa deuda en cada consulta.

§2 Objetivos

  • O1. El cambio queda en una única migración nueva V3__align_rbac_naming.sql; git diff desde la rama base muestra solo ese archivo (V1/V2 intactas).
  • O2. Las 3 tablas con auditoría (app_users, app_roles, app_permissions) exponen creado_en y actualizado_en, y dejan de exponer created_at/updated_at en information_schema.columns.
  • O3. Cero códigos FIELDS_* en app_permissions; existen SEMBRADIOS_CREATE/READ/UPDATE/DELETE con sus ids originales.
  • O4. La matriz queda simétrica: existen EVIDENCE_UPDATE, DIAGNOSES_DELETE y RECOMMENDATIONS_DELETE (ids contiguos …0803, …1004, …1104) y cada rol recibe los permisos nuevos según su perfil.
  • O5. V3 aplica sin error tanto en una BD nueva (V1→V2→V3) como sobre una BD que ya tenía V1/V2 aplicadas (checksum sin cambios).
  • O6. flyway validate devuelve OK y flyway_schema_history registra la fila V3 con checksum.

§3 Fuera de alcance

  • No se arregla el build roto (pin Flyway 13.5.0 vs Spring Boot 3.4.1 → NoSuchMethodError). Es prerrequisito documentado: esta migración se valida con el plugin Maven de Flyway o después de la spec de estabilización; no es defecto de esta entrega.
  • No se recupera ni se ajusta el módulo auth (entidades JPA de feat/rbac-enterprise). Queda documentada la dependencia: al recuperarlo hay que mapear los nombres nuevos.
  • No se rediseña el catálogo de permisos desde la vista de producto (fuera del MVP; requiere otra especificación).
  • No se crean las tablas del dominio MVP (Agricultor, Sembradio, Consulta…): no existen entidades aún; corresponde a la spec del MVP.
  • No se toca el frontend ni main.

§4 Diseño

El trabajo produce una sola migración versionada de Flyway. Flujo de 4 pasos: (1) computar el delta real entre V1/V2 y data-model-mvp.md; (2) escribir V3__align_rbac_naming.sql con los renames, el renombrado de códigos y los permisos nuevos; (3) aplicarla contra una BD PostgreSQL y dejar que Flyway la registre; (4) verificar con el lote SQL del checklist de aceptación.

Contenido concreto de V3 (reglas de diseño, no el script final):

  • ALTER TABLE sobre app_users, app_roles y app_permissions: created_at → creado_en, updated_at → actualizado_en, conservando defaults existentes.
  • UPDATE app_permissions SET code='SEMBRADIOS_CREATE' WHERE code='FIELDS_CREATE' (y READ/UPDATE/DELETE). Se renombra el code, nunca el id: los joins de app_role_permissions van por id y no se tocan.
  • INSERT … ON CONFLICT DO NOTHING de los 3 permisos nuevos con ids contiguos (…0803, …1004, …1104).
  • INSERT … SELECT ON CONFLICT DO NOTHING de asignaciones: EVIDENCE_UPDATE → AGRICULTOR y ADMIN; DIAGNOSES_DELETE y RECOMMENDATIONS_DELETE → AGRONOMO, EXTENSIONISTA y ADMIN.
  • Las tablas app_* se conservan como infra RBAC separada del modelo de dominio.

§7 Decisiones

Duda que aparecióSe eligióSe descartóPor qué
Cómo cambia el esquema sin romper Flyway Migración nueva V3 aditiva Reescribir V1/V2 y resetear dev; solo documentar la deuda V1/V2 ya están aplicadas en dev y registradas en flyway_schema_history; reescribirlas rompería checksums y datos. "Solo documentar" no resuelve la contradicción con la fuente única.
Forma de los nombres nuevos snake_case español (creado_en, actualizado_en, SEMBRADIOS_*) camelCase literal del doc (creadoEn); mantener inglés (created_at, FIELDS_*) snake_case es la convención SQL estándar, evita identificadores entrecomillados en Postgres y cumple el idioma de la fuente única; camelCase obliga a comillas en cada query y mantener inglés deja la deuda viva.
Permisos faltantes (EVIDENCE_UPDATE, DIAGNOSES_DELETE, RECOMMENDATIONS_DELETE) Completar la matriz simétrica Dejarlos como huecos; redefinir el catálogo desde producto Un catálogo con huecos obliga a casos especiales en cada verificación; redefinirlo desde producto está fuera del MVP y merece su propia especificación.
El auth de feat/rbac-enterprise mapea estas tablas Fuera de alcance; dependencia documentada Recuperar y adaptar las entidades JPA del auth en este mismo trabajo Recuperar el auth es otro trabajo con su propia decisión de producto; mezclarlo aquí infla esta entrega. Al recuperarlo, sus entidades deberán usar los nombres nuevos.
Las tablas app_* vs el modelo de dominio Se conservan como infra RBAC separada Fusionarlas o renombrarlas al dominio (Agricultor, Sembradio…) Son dos conceptos distintos: quién puede acceder (RBAC) vs qué produce el negocio (dominio). Renombrarlas ahora sin entidades de dominio crearía un modelo fantasma.
